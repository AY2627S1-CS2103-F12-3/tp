Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Model component

Address values are normalized at the model boundary: leading and trailing Unicode whitespace is removed, consecutive whitespace is collapsed to one space, and an address containing only Unicode whitespace (including U+2002 en spaces) is rejected.

API : Model.java

The partial diagram focuses on role associations. Filtered-view associations and candidate fields are omitted for clarity; the fields of a candidate are shown in the diagram below.

A candidate (Person) is immutable and always has exactly one of each field except tags:

  • Two candidates are the same person if they share an email (ignoring case) or a phone number. Names are not compared, as different candidates can share a name.
  • The candidate's role is a RoleTitle, the same class that names a Role.
  • An empty Note means the candidate has no note. New candidates share the empty Note.NONE, so the association to Note is not a composition.
  • Interview.NONE means the candidate has no interview, and is the only Interview without a date and time. It is shared by every such candidate, so the association to Interview is not a composition. See Candidate interviews.
  • A new candidate's Status is RESUME.

The Model component,

  • stores candidates (Person) in UniquePersonList and roles (Role) in UniqueRoleList, both owned by AddressBook. ReadOnlyAddressBook exposes unmodifiable observable views of both collections.
  • maintains filtered candidate and role lists in ModelManager, exposed through getFilteredPersonList() and getFilteredRoleList(). The UI observes these lists so additions, replacements, and removals update the relevant list panel.
  • represents each role as an immutable title, required experience level, and RoleStatus (OPEN or CLOSED). One role is one vacancy; no opening count is stored.
  • stores each candidate's association as a RoleTitle, not a separate copy of a Role. Role lookups match titles without case sensitivity.
  • derives role-card summaries through RoleCandidateCounts, an immutable snapshot of candidate-status totals. This helper is omitted from the partial association diagram and is not part of stored role data.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • saves candidates and roles together in the address book JSON file, and user preferences in a separate JSON file. It reads them back into corresponding model objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • uses JsonSerializableAddressBook with JsonAdaptedPerson, JsonAdaptedTag, and JsonAdaptedRole to convert between JSON-compatible values and model objects. A role's saved fields are title, experienceLevel, and status; the status is the exact enum name.
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Offline command guide

HelpCommandParser accepts zero or one command name. More than one token is rejected with the dedicated extra-argument message. AddressBookParser recognizes the help keyword without case sensitivity, without changing dispatch for other commands.

HelpCommand returns a non-undoable CommandResult containing CommandGuide#getOverview() when no topic is supplied, or CommandGuide#findHelp() for a single topic. Lookup uses Locale.ROOT so case-insensitive matching is independent of the machine's language settings. Unknown topics produce a CommandException naming the original input; neither failure path changes the model. CommandGuide keeps instructions in a stable command order and reuses existing MESSAGE_USAGE definitions where available. This avoids a second source of truth for command parameters and examples.

MainWindow displays help in the existing ResultDisplay, with additional height, wrapped text and vertical scrolling. The Help menu and F1 use the same overview without opening a separate window. Both recruitment lists remain visible; no filter or recruitment record changes.

LogicManager skips the normal save specifically for HelpCommand. Reading instructions therefore works even when saving recruitment data would fail, and does not create an undo snapshot or discard redo history. Other commands retain their existing saving behavior. Help is bundled with the JAR and needs no network connection or additional files.

Candidate Statuses

Representation and Persistence

The 'Status' enum defines seven candidate statuses: RESUME, INTERVIEW, OFFER, DECISION, HIRED, REJECTED, and WITHDRAWN. The first four are pending statuses; the remaining three are final statuses. New candidates are assigned the RESUME status by default.

When stored candidate data has no status, loading it defaults to RESUME. Upon successful execution of any command except HelpCommand, LogicManager saves the complete address book, and JsonAdaptedPerson writes each status using its exact enum name. Viewing help does not trigger a save.

An unrecognized stored value causes data loading to fail and invokes the recovery process described in Protecting unreadable recruitment data.

Batch Status Updates

Batch status updates of candidate statuses is handled by the status command.

StatusCommandParser requires exactly one st/ prefix. It splits the preamble on whitespace, parses each index using ParserUtil#parseIndex, and stores the results in a set, removing duplicate indices. ParserUtil#parseStatus trims and uppercases the supplied value before matching it to a Status.

StatusCommand resolves every index against the currently displayed candidate list, and creates replacement Person objects with the requested status, updates the model, resets the candidate filter to show all candidates, and returns a success result.

During running of StatusCommandParser, ParseException will be thrown on any of these conditions:

  • No st/ prefix found.
  • Multiple st/ prefixes found.
  • One of the indices is not a nonzero unsigned integer.
  • Normalized status does not match one of the Status values.

During running of StatusCommand, CommandException will be thrown on any of these conditions:

  • Index falls outside filtered candidate list.
  • A pending status (RESUME, INTERVIEW, OFFER or DECISION) is being assigned to a candidate whose role is closed. (This is to ensure that closed role only ever contains candidates with a final status).
  • Assigning a HIRED status gives a role more than one hired candidate, whether the conflict comes from an existing candidate or another candidate within the batch.

Because these checks precede mutation, failures leave all candidates unchanged.

Role creation and persistence

Role identity and validation

RoleTitle strips surrounding whitespace, validates 1–100 Unicode code points and the allowed characters, and requires at least one letter. Allowed punctuation includes apostrophes, ampersands, hyphens, slashes, full stops, plus signs, hashes, parentheses and commas, so titles such as C++ Developer, C# Developer, Engineer (Backend) and Manager, Sales are accepted. The same value object validates role creation, renaming, candidate associations and saved titles; punctuation is retained and remains significant when comparing titles. ExperienceLevel similarly strips its value and validates 1–50 printable code points, excluding control, format, surrogate, unassigned, line-separator, and paragraph-separator characters. Their constraint messages use the same length constants as their validation, avoiding independently hard-coded limits.

RoleTitle#MESSAGE_CONSTRAINTS also lists the allowed characters on a second line, so a title with an unsupported symbol is not explained only by its length and letter requirements. Construction, command parsing and JSON role/candidate validation reuse this same message.

Role#isSameRole compares only titles through RoleTitle#isSameTitle, ignoring case. UniqueRoleList uses that identity to reject duplicates, irrespective of experience level or open/closed status. Full Role#equals also compares experience level and status; it is not the duplicate rule. Internal spaces are not collapsed. The immutable Role constructor without a status creates an OPEN role.

Adding an opening

AddressBookParser routes role to RoleCommandParser, which delegates add to AddRoleCommandParser. The parser tokenises r/ and x/, checks missing fields, reuses ArgumentMultimap#verifyNoDuplicatePrefixesFor, rejects a non-empty preamble, and validates both values through ParserUtil. Missing-prefix errors therefore take precedence over repeated-prefix or invalid-value errors when several problems occur together.

AddRoleCommand checks Model#hasRole before calling Model#addRole. The model updates the underlying observable collection and resets the role filter to show all roles. The command returns Added open role: TITLE.; the roles list displays the updated roles and the candidates list retains its filter, if any. Parsing or duplicate rejection leaves the stored records unchanged.

Correcting a role's title or required experience

RoleCommandParser delegates edit to EditRoleCommandParser. The parser reads the displayed-role index with ParserUtil#parseRoleIndex, rejects repeated r/ or x/ prefixes using the existing duplicate-prefix helper, and requires at least one editable field. Supplied values use ParserUtil#parseRoleTitle and ParserUtil#parseExperienceLevel; omitted fields are left unchanged. An invalid index is reported first, followed by duplicate prefixes, missing fields, title validation and experience validation.

EditRoleCommand resolves the index against Model#getFilteredRoleList. It constructs the complete replacement role, preserving its status and omitted fields, then checks the full role collection for a different role with the requested title. Duplicate comparison ignores case and surrounding whitespace, including closed roles; capitalization corrections to the selected role are allowed. The shared duplicate-role message is held in Messages. Corrections never reopen recruitment or merge two openings.

Model#setRole delegates to AddressBook#setRole. The model validates the role replacement through UniqueRoleList before changing either collection. If the title's exact spelling changes, every candidate whose old title matches case-insensitively is updated to the new title using Person#withRole. This includes candidates hidden by the current filter. Their other details and order are unchanged; unrelated candidates retain their existing instances. An experience-only edit does not replace candidate objects. The existing observable lists are retained, so role and candidate cards refresh without new UI components. Filter predicates are retained and reevaluated after list changes.

The result shows Edited role: TITLE. with the updated title. EditRoleCommand logs accepted corrections and rejected duplicate titles; LogicManager saves both collections through the existing path. Parser or command-validation failures leave records, filters and the saved file unchanged. The existing save-error behavior described below remains unchanged: this is not a transactional filesystem save. Once renamed, a role's old title is available again; no title alias or storage-schema migration is introduced.

The sequence below starts after parser validation. Nested alternatives reject an invalid index or a duplicate title before either list changes. Only the valid branch calls setRole, which replaces the role before propagating its new title across the full candidate list. Candidate copying is shown as a single action to omit unrelated field-construction details. Saving occurs in LogicManager after the command returns successfully, as described below.

Saving and restoring associations

After a command other than HelpCommand executes successfully, LogicManager#execute asks Storage to save the complete address book, including both collections. This also happens for successful read-only commands such as list. HelpCommand returns before the save call, so viewing help neither creates the recruitment data file nor retries a failed save. After resolving a file-access problem, the user can run list successfully to retry saving.

When running AddressBook from a JAR file, data/addressbook.json, preferences.json, and the log files are saved in the directory containing the JAR. When running from compiled classes, they are saved in the process's working directory.

Parsing and command-validation failures do not reach the save call. Save errors become CommandExceptions; earlier in-memory changes are not rolled back. Normal command saves are not transactional and do not create backups. Startup recovery below handles unreadable data separately.

JsonSerializableAddressBook#toModelType reconstructs roles before candidates. Each JsonAdaptedRole validates its required fields and exact OPEN/CLOSED enum name. Duplicate titles are rejected using the same identity rule as the model. Each candidate must then reference an existing role; the loader replaces the candidate's role title with that role's canonical stored title. Closed roles are valid references because closure retains candidates.

An absent roles array is treated as empty, but loading still fails if a candidate lacks a role or references a missing one. A missing candidate status defaults to RESUME, whereas a missing role status is invalid. There is no automatic migration from old contact-only records. Loading validates fields, duplicate records, and references; it does not enforce all command-level recruitment rules, such as the maximum number of hired candidates in hand-edited data.

Protecting unreadable recruitment data

Invalid data is reported as DataLoadingException. JSON null roots and null candidate, role or tag entries also fail loading rather than bypassing the failure path with a null-pointer exception. JsonUtil#fromJsonString reads through a managed Jackson parser and checks for end of input after deserializing the first value. Additional root values or malformed trailing text fail loading; ordinary surrounding whitespace remains valid. This prevents a later save from silently discarding content that Jackson would otherwise ignore. Recovery preserves the entire original file, not just the first object, and does not attempt to combine multiple objects. JsonUtil#readJsonFile returns an empty optional only when the file is known not to exist; an indeterminate existence check does not silently treat an inaccessible file as missing.

MainApp#init attempts recovery after a recruitment-data loading failure. RecruitmentDataRecovery first checks that the source is a regular file without following symbolic links, then moves it to a sibling .bak path. Files.move does not use REPLACE_EXISTING: an existing backup, including one created after the naming decision, is not replaced. A local timestamp in yyyyMMdd-HHmmss-SSS format and then a numbered suffix resolve collisions. The format avoids characters forbidden in Windows filenames. The original bytes are moved, not parsed, repaired or partially imported.

Only after backup succeeds does recovery write an empty JsonSerializableAddressBook at the original path using CREATE_NEW. This refuses to overwrite a file that appears during recovery. Persisting the empty replacement before initializing commands also makes the next startup stay empty, even if the user exits without executing a command. The existing missing-file sample-data policy is not used for this recovery path.

MainApp#start asks UiManager to show a warning on the JavaFX thread before opening the command window. The warning names the full backup and replacement paths and explains manual restoration. No automatic merge is attempted: users must preserve new records separately before restoring. StartupDataNotice holds the notification text and fatal/non-fatal outcome independently of JavaFX. Lifecycle tests capture those real notices through the notification boundary; separate notice tests check paths and restoration instructions without substituting the message-generation logic.

If backup or replacement creation throws an I/O or security exception, initialization returns before creating the model, logic or command UI. The startup error names the original path, failure reason, and backup path if the move succeeded. JavaFX shuts down after dismissal. A directory or symbolic link is not moved. MainApp#stop skips preference saving when no model was initialized. Preference loading still runs before recruitment data is loaded. Preference files use the same single-root JSON check; invalid preferences retain the existing default-settings fallback rather than using recruitment-data backup recovery.

The activity diagram below follows the failed-loading path after preferences and storage have been initialized. FILE denotes the original data filename (normally addressbook.json), and TIMESTAMP is captured once for the recovery attempt. A move that reports an existing destination selects the timestamped name, then -1, -2, and so on. The loop retries the move itself rather than relying on an earlier existence check. Source-check or move failures stop startup with the original at its source path; replacement failures stop startup with the original in the remembered backup. Only successful preservation and replacement lead to empty lists, a recovery warning, and an open command window.

Recovery preserves the source before exposing any command that can reach the normal save path. If recovery cannot complete safely, startup remains blocked rather than risking the original or its backup. If the file is genuinely absent instead, startup still uses SampleDataUtil#getSampleAddressBook. A valid empty file loads empty lists, not sample data.

Recovery diagnostics follow the same lifecycle: MainApp emits a loading WARNING, RecruitmentDataRecovery records each completed backup and replacement at INFO, and unsafe recovery ends with a SEVERE event from MainApp. Success messages name the paths actually used and are not emitted for a stage that failed. Existing startup and recovery tests now check these events alongside preserved file contents and the absence of a command UI after failure. The shared LogCapture test utility restores logging configuration after each capture. See Recovery diagnostics for interpretation and privacy limitations; no extra production logging or recovery-policy change is needed.

Role lifecycle and candidate safeguards

Closing recruitment

RoleCommandParser delegates close to CloseRoleCommandParser. Close and delete share ParserUtil#parseRoleIndex to reject missing, invalid, or extra index arguments consistently. CloseRoleCommand resolves the index against Model#getFilteredRoleList and rejects an already closed role.

Candidate checks use the complete ReadOnlyAddressBook#getPersonList, not the filtered candidate list, matching role titles without case sensitivity. Status#isPending classifies statuses RESUME, INTERVIEW, OFFER and DECISION as pending. Closure rejects pending candidates with their count, then rejects more than one hired candidate. No candidates, or no hired candidate, is allowed. After validation, Model#setRole replaces the immutable role with a CLOSED copy. Candidate records and statuses remain unchanged. The observable role list refreshes, and LogicManager saves the change. AddCommand rejects new candidates for closed roles.

Deleting an unused role

RoleCommandParser delegates delete to DeleteRoleCommandParser. DeleteRoleCommand applies the same index guards, then counts associated candidates across all stored records. Any associated candidate blocks deletion, irrespective of status or visibility; the error includes their count. An empty role may be deleted whether OPEN or CLOSED.

Deletion goes through Model#deleteRole, AddressBook#removeRole, and UniqueRoleList#remove. The role list refreshes and its indices update. LogicManager saves the removal. Deletion releases the title for reuse but never deletes, detaches, or reassigns candidates. Deletion takes effect immediately, but can be undone in the current session.

Undoing and redoing role changes

Close and delete inherit Command#isUndoable returning true. Before execution, LogicManager asks ModelManager#recordAddressBookState to retain a complete AddressBook snapshot, including roles and candidates. Successful execution clears redo history through commitAddressBookState; an execution failure discards the pending snapshot instead.

undo and redo restore these snapshots in reverse and forward order respectively, and LogicManager saves the restored records. Undo can therefore restore a deleted role or reverse a closure without a dedicated reopen command. Later changes must be undone first. The history stacks are held in memory only: restarting loads saved records but does not restore undo or redo history. Run list role after undo or redo to display the updated roles; listing does not change history.

Status changes and one hire per role

Before assigning HIRED, StatusCommand checks amongst candidates to be assigned the HIRED status, as well as all stored candidates with the HIRED status, for another candidate with a case-insensitively matching role title, excluding the selected candidate by candidate identity. Applying or reapplying HIRED to that candidate is allowed only if there is no other hire. Moving an existing hire to another permitted status frees the vacancy; hiring a candidate never closes the role automatically.

Before assigning a pending status (RESUME, INTERVIEW, OFFER or DECISION), the command looks up the candidate's role and rejects the change if the role is closed. Final-to-pending corrections remain available for open roles. Corrections between final outcomes remain available for closed roles, subject to the hiring guard. Both guards run before replacing a candidate or changing filters. Rejected commands do not trigger saving.

Keeping displayed indices aligned with the UI

Both candidate and role lists remain visible at all times. Candidate commands resolve indices against Model#getFilteredPersonList, while role commands use Model#getFilteredRoleList. Each list has independent numbering; filtering candidates changes candidate indices but not role indices.

Candidate-status totals on role cards

RoleCandidateCounts scans a supplied candidate collection for a case-insensitively matching RoleTitle, then snapshots counts by Status. Pending totals use Status#isPending rather than hard-coded pending-status names. Each candidate contributes once, and an absent category returns zero. The summary reports actual records, including any inconsistent hand-edited hire counts; it never changes statuses or enforces command-level recruitment rules.

Logic#getPersonList exposes the address book's unmodifiable observable candidate list, not the filtered list used by the candidate panel. MainWindow passes it to RoleListPanel alongside the existing observable role list. A panel-lifetime candidate listener refreshes the role list after additions, replacements, removals, and resets. List cells construct fresh summaries when rendering their roles, including when scrolling. Listeners are not attached to individual recycled cells. Role replacements still use the existing role-list binding.

RoleCard displays four explicit labels in a wrapping FlowPane. Cards bind their width to the available list-cell width, so long role details wrap without forcing horizontal scrolling. Role indices retain their full width beside wrapped titles. Both open and closed roles use the same calculation. Counts are not cached in Role or saved to JSON, so loading data reconstructs them without a schema migration or a second source of truth. Candidate filters, role order, indices, and command feedback are unchanged.

Unit tests cover classification, title matching, empty states, snapshots, and mixed-role data. Logic integration tests check unfiltered observation, status changes, additions, deletion, role reassignment through the edit command and model API, resets, and reload. The existing Codecov exclusions for RoleCard, RoleListPanel, and MainWindow remain unchanged; manual packaged-JAR tests cover their rendering and refresh wiring rather than treating excluded UI code as automatically verified.

Correcting a candidate's role

EditCommandParser accepts r/ as an optional, non-repeatable edit field. It uses ParserUtil#parseRoleTitle for the existing title constraints and stores the result in EditPersonDescriptor, including its copy, equality and diagnostic-string behaviour.

EditCommand resolves an explicitly requested role through Model#findRole before replacing any records or changing filters. A missing role is rejected; a different role must be open. The source may be open or closed, and selecting the existing role remains a permitted no-op. Resolution uses case-insensitive matching and the stored role's canonical spelling. Omitting r/ preserves the role. The shared EditCommand#isRoleChanged predicate keeps the closed-destination and hiring guards consistent about whether the operation actually transfers the candidate.

The edited immutable Person keeps its status and note, and keeps every other field not explicitly edited. The existing candidate-identity duplicate check is unchanged. For a real role transfer, CandidateRoleChecks#verifyHiringAllowed rejects a HIRED candidate if another stored candidate for the destination is hired. It uses all records, not the filtered list, and excludes the original candidate by identity rather than the edited name. StatusCommand validates batch status changes separately: before changing any candidate, it checks both existing hires across all stored candidates and conflicting hires within the selected batch. Both workflows enforce one hired candidate per role; they share error messages, not the validation method.

After validation succeeds, Model#setPerson updates the candidate collection and the candidate filter resets to show all records. The existing Edited candidate: ... result formats the updated candidate, including the new name and canonical role. Normal LogicManager saving persists the association without a JSON schema change. Validation failures leave records and filters unchanged and do not save. Neither role's status changes automatically.

Role workflow diagnostics and internal checks

Role commands and candidate-role transfers reuse LogsCenter, with INFO for successful in-memory changes and FINE for expected recruitment-rule rejections. Closure and deletion refusals include relevant candidate counts, while successful indexed operations identify the displayed index. These events precede storage saving and never claim that persistence succeeded. The messages omit candidate names, contact details, notes and raw commands; the pre-existing central command log is not covered by this restriction. See the logging guide for levels and limitations.

Assertions check programmer assumptions rather than user input. CandidateRoleChecks#verifyHiringAllowed requires a non-null internal status so a caller cannot accidentally bypass the single-hire check by omitting it. EditCommand#resolveRole checks that Model#findRole returns a title matching the request before any mutation. Candidate input, missing roles, closed destinations and duplicate hires still use normal validation and CommandException; disabling assertions does not disable those checks. Existing collection null and uniqueness checks remain unchanged. No essential work is performed inside an assertion.

RoleWorkflowDiagnosticsTest checks operation logs and their levels, guards against logging candidate details, and verifies unchanged state after refusal. Focused contract tests inject programmer errors before mutation, while the existing role, transfer, integration and persistence tests exercise valid paths. See the testing guide for assertion-enabled and assertion-disabled checks. Command formats, success/error messages, UI behavior and the storage schema are unchanged.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Candidate email validation

Email checks the part before the @ (the local part) and the part after it (the domain) separately. The local part follows the unquoted (dot-atom) form of RFC 5322, which is also the form the HTML standard accepts for email inputs. It may contain letters, digits and the symbols ! # $ % & ' * + - / = ? ^ _ ` { | } ~, with dots only between other characters, so a dot is never first, last, or next to another dot. The domain follows the rules for internet host names: parts separated by dots, each made of letters, digits and hyphens, and not starting or ending with a hyphen. The last part must be at least 2 characters long, as every top-level domain such as com or sg is. Hyphens may be consecutive inside a part, as in the encoded non-English domain xn--80ak6aa92e.com.

Email#findValidationError is the only validator. It runs the checks in a fixed order (the @, then the part before it, then the domain) and returns a message naming the first problem found, such as Email cannot contain “,” before the @. Email#isValidEmail returns true exactly when findValidationError finds nothing, so the error messages cannot disagree with what is rejected. Both ParserUtil#parseEmail and JsonAdaptedPerson show the specific message. Related problems share one message where the cause is easy to spot once the user knows which part to look at, such as a dot that comes first, last, or twice in a row before the @.

Two kinds of valid email are likely typos. Email#getUncommonSymbols returns the symbols before the @ other than . _ - + ', which major email providers do not issue, such as # in john#doe@example.com. Email#hasDotlessDomain returns true for a domain such as gmailcom. Email accepts both, but AddCommand and EditCommand add a warning for each to their success message through EmailChecks#appendEmailWarnings, which works like PhoneChecks#appendPhoneWarnings. EditCommand checks the email only when it changes, ignoring case, so editing another field of a candidate does not repeat the warnings. Loading the data file never warns.

Design considerations

Aspect: Which local parts are accepted

  • Alternative 1 (current choice): The unquoted form of RFC 5322, with a warning for symbols other than . _ - + '.
    • Pros: Every address that an email provider issues is accepted, the rule comes from a published standard, and a typo such as john#doe@example.com is still flagged.
    • Cons: The user can ignore the warning and keep an address that is a typo.
  • Alternative 2: Only letters, digits and . _ - + ', the symbols that major email providers issue.
    • Pros: A typo with another symbol can never be saved.
    • Cons: Rejects some valid addresses.
  • Alternative 3: All of RFC 5322, including quoted local parts such as "john doe"@example.com.
    • Pros: Accepts every valid address.
    • Cons: A quoted local part can contain spaces and text such as a/, which ArgumentTokenizer would read as the start of another field. Major email providers also do not issue such addresses.

Aspect: How a domain without a dot is handled

  • Alternative 1 (current choice): Accept it and warn.
    • Pros: Catches a likely typo, such as gmailcom for gmail.com, without rejecting a valid address.
    • Cons: The user can ignore the warning and keep an address that is a typo.
  • Alternative 2: Reject it.
    • Pros: A typo can never be saved.
    • Cons: Rejects valid addresses.

Candidate phone numbers

Phone accepts 8 to 15 digits with an optional leading +, and removes spaces and hyphens before saving. Two kinds of phone problems are checked when a candidate is added or their phone number is edited:

  • Exact duplicates are rejected. Person#isSamePerson compares phone numbers with Phone#equals, which compares the saved digits exactly. UniquePersonList and the data-file loader use the same rule.
  • Possible problems only add a warning to the success message. PhoneChecks#appendPhoneWarnings runs after AddCommand or EditCommand has stored the candidate. EditCommand calls it only when the phone number changes, so an unchanged number is not flagged again.
    • Phone#isPlausibleNumber treats a number without a +, or with +65, as a Singapore number, which has 8 digits starting with 3, 6, 8 or 9. Numbers with another country code are not checked, since overseas formats vary.
    • Phone#isPossiblySameNumber compares numbers after removing the + and, if 65 is followed by exactly 8 digits, the 65. So +6591234567, 6591234567 and 91234567 may be the same number, but are not exact duplicates.

Design considerations

Aspect: What to do with a number that may be another candidate's

  • Alternative 1 (current choice): Accept it and add a warning naming the candidates whose number may be the same.
    • Pros: A real but unusual number, such as an overseas number written without its +, is never blocked.
    • Cons: The user may miss the warning and keep a duplicate.
  • Alternative 2: Reject it, like an exact duplicate.
    • Pros: Duplicates cannot be added by mistake.
    • Cons: Wrongly blocks different numbers that happen to match, such as an overseas number without its country code. The loader would also have to reject such pairs, so data files saved by older versions could stop loading.

The loader must keep using only the exact rule. Otherwise, a pair of candidates accepted with a warning could be saved in a file that then fails to load.

Candidate notes

Each Person has a Note, a free-text field for details such as a candidate's skills or availability. Interview dates and times have their own field, described in Candidate interviews. The candidate card shows the note as Note: NOTE. An empty note means the candidate has no note, and the candidate card hides it.

Recording a note

NoteCommandParser splits the arguments into the first word, which is parsed as the index, and the rest, which is trimmed and becomes the note. It does not use ArgumentTokenizer, so the note can contain text that looks like a prefix, such as t/ or n/. An empty remainder gives an empty Note, so note 1 clears the first candidate's note.

NoteCommand#execute looks up the candidate in the displayed candidate list and replaces it with a copy that has the new note. It does not reset the candidate filter, so a recruiter can add notes to a filtered list by its displayed numbers. The result message compares the previous note with the new one, so it says whether a note was added, replaced or cleared. It does not repeat a new note, since the candidate card shows it. Clearing a note suggests undo and shows the cleared note, since the user cannot see it anywhere else. Other commands that rebuild a Person, such as edit, status, and interview, copy the existing note across, so they never change it.

Notes are stored as the note field of each candidate in the JSON data file. A candidate saved without a note field loads with an empty note.

Design considerations

Aspect: How the note is entered

  • Alternative 1 (current choice): A separate note INDEX [NOTE] command that takes everything after the index.
    • Pros: Any text can be stored, including text that looks like a prefix.
    • Cons: A note cannot be given when the candidate is first added, so it takes a second command.
  • Alternative 2: An nt/NOTE prefix on add and edit.
    • Pros: Consistent with the other candidate fields.
    • Cons: The tokenizer ends the note at the next prefix. For example, nt/Discuss t/java would save the note Discuss and add a java tag, so valid notes are silently changed. This alternative was implemented and then removed for this reason.

Aspect: Replacing or adding to a note

  • Alternative 1 (current choice): note INDEX NOTE replaces the whole note, and note INDEX clears it.
    • Pros: One simple command covers setting, correcting and clearing a note. The result message says when a note was replaced or cleared, so a note is never overwritten silently, and undo restores a note changed by mistake.
    • Cons: To add to a note, the user types the whole note again.
  • Alternative 2: A way to add text to the end of an existing note.
    • Pros: Saves retyping when a recruiter adds details after each recruitment stage.
    • Cons: It needs its own command word. A marker inside note, such as a leading +, would clash with notes that start with that text, such as +65 9123 4567 (home). It is planned for a future version, and the User Guide lists it as not supported yet.

Candidate interviews

Each Person has an Interview, which holds the date and time of the candidate's interview, to the minute. A candidate with no interview has Interview.NONE, so no code needs to handle a null interview. The candidate card shows the interview as Interview: YYYY-MM-DD HH:MM, and hides the line for Interview.NONE.

Validating a date and time

Interview accepts only zero-padded YYYY-MM-DD HH:MM values that are real dates and valid 24-hour times. It checks a value in two steps, so that each kind of mistake gets its own error message:

  1. Interview#isValidFormat checks the shape with a regular expression. A value such as 2026-10-20 9:00 fails here, and the user is told the expected format.
  2. Interview#isValidDateTime parses the value with the pattern uuuu-MM-dd HH:mm and ResolverStyle.STRICT. A value with the right shape but an impossible date or time, such as 2026-02-30 or 24:00, fails here, and the user is told the value does not exist.

Strict resolving is needed because the default resolver silently adjusts 2026-02-30 to 2026-02-28. The pattern uses uuuu (year) instead of yyyy (year of era), because strict resolving rejects every yyyy year that has no era. The Interview constructor enforces both checks with checkArgument, so an invalid interview cannot be created even when assertions are disabled. Past dates are allowed, so recruiters can record interviews that have already happened.

Scheduling or clearing an interview

InterviewCommandParser tokenizes the arguments with the d/ prefix. The preamble must be exactly one index. A missing index, an index joined to d/ without a space, an index that is not a positive whole number, and extra text after the index each get their own error message, so the user can tell what to correct. If d/ is present, ParserUtil#parseInterview runs the two checks above and creates the Interview. If d/ is left out, the parser uses Interview.NONE, so interview 1 clears the first candidate's interview. An empty d/ is rejected with the format error instead of clearing the interview, so a user who forgets to type the date does not lose the existing one.

The sequence diagram below shows how InterviewCommandParser parses interview 1 d/2026-10-20 14:00, and the branch that clears the interview when d/ is left out. The steps before and after parsing are the same as for delete (see the Logic component).

InterviewCommand#execute looks up the candidate in the displayed candidate list and replaces it with Person#withInterview, a copy that has the new interview. A candidate has only one interview, so scheduling another one replaces the previous interview, and interview INDEX replaces it with Interview.NONE. Like note, it does not reset the candidate filter, so a recruiter can schedule interviews for a filtered list by its displayed numbers. Clearing a candidate with no interview, or giving the same date and time again, succeeds without changing the data, as note does for notes.

After saving a new interview, InterviewCommand checks whether it might be a mistake and adds a line to the result message for each of these cases, in this order:

  • The candidate's status is final (HIRED, REJECTED or WITHDRAWN), using Status#isPending, and the interview is today or later. This line comes first, as it suggests the interview may not be needed at all. A past interview is not checked, as recording one is how a recruiter keeps the history of a candidate who already has an outcome.
  • The date is before today, or more than a year after today. The interview is still saved so that historical interviews can be recorded, but the warning helps catch a mistyped year. Today's date comes from a Clock, which is the system clock in the app and a fixed clock in tests.
  • Other candidates in the whole address book, including those hidden by the filter, have an interview at the same date and time. The line Also at this time: shows at most two names, shortens names longer than 30 characters, and reports how many additional candidates share the slot.

Clearing an interview is never checked.

Other commands that rebuild a Person, such as edit, note, and status, copy the existing interview across, so they never change it.

Saving and loading interviews

Interviews are stored as the interview field of each candidate in the JSON data file, in the same YYYY-MM-DD HH:MM form. Interview.NONE is saved as an empty string. When loading, a missing, null, or empty interview field gives Interview.NONE, so data files saved before interviews existed still load. Any other value goes through the same two checks, and an invalid value stops the file from loading, as an invalid phone number does.

Design considerations

Aspect: Where the interview is stored

  • Alternative 1 (current choice): A separate Interview field with its own command.
    • Pros: The date and time are checked, so impossible or mistyped slots are rejected. The value can later be used to sort candidates by interview time.
    • Cons: Every place that rebuilds a Person must copy the new field, or that command would silently clear the interview.
  • Alternative 2: Keep interviews in the free-text note.
    • Pros: No new field or command.
    • Cons: Nothing checks the date, and the date cannot be compared or sorted.

Aspect: How "no interview" is represented

  • Alternative 1 (current choice): An Interview.NONE value, whose date and time is held in a private nullable field and returned as an Optional<LocalDateTime>.
    • Pros: Person fields are never null, and the null never leaves the Interview class.
    • Cons: Code that needs the date and time must handle the empty Optional.
  • Alternative 2: A sentinel date, such as 0000-01-01 00:00.
    • Pros: Every interview has a real LocalDateTime.
    • Cons: The sentinel could be shown or sorted as if it were a real interview, and a user could enter the same value.

Aspect: How unusual interviews are handled

  • Alternative 1 (current choice): Save the interview and add a line to the result message.
    • Pros: Each case can be legitimate, such as a panel interviewing two candidates at once, or recording an interview for a candidate who was later rejected. The recruiter is not blocked, but still sees a likely mistake.
    • Cons: A recruiter who does not read the result message can miss the warning.
  • Alternative 2: Reject the interview.
    • Pros: A mistyped year cannot be saved.
    • Cons: Valid interviews would be refused, and the recruiter would need a way to override the check.

Non-Functional Requirements

  1. RecruiterBuddy should support all its documented functions on Windows, macOS, and Linux with Java 25 as the only installed Java version.
  2. Should be able to hold up to 1000 candidates and 1000 roles without noticeable sluggishness in performance for typical usage.
  3. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.
  4. With Java 25 installed, a user should be able to launch RecruiterBuddy without running an application installer or separately installing additional runtime dependencies. Extracting a ZIP file is permitted.
  5. RecruiterBuddy should be distributed as a single JAR file or, if additional files are necessary, a single ZIP file containing the JAR and those files. The distribution should not exceed 100 MB.
  6. All documented functions that operate on locally stored application data should remain usable without an Internet connection. Following links to external websites is excluded.
  7. GUI elements should be fully visible and work well on screen resolutions 1920x1080 and higher, and screen scales 100% - 125%.
  8. GUI elements should be usable on screen resolutions 1280x720 and higher, and screen scales 150%.
  9. After application data has been successfully saved, closing RecruiterBuddy normally and reopening it with the same unchanged data files should restore the saved data, including all saved additions, modifications, and deletions.
  10. A new user should be able to learn all basic commands (adding, updating and deleting candidates and roles) within 30 minutes
  11. The application should carry out a user action and give visual confirmation within 1 second of input.
  12. A command rejected because of invalid syntax or invalid input values should leave recruitment records and user-defined configuration unchanged, both in memory and in saved data file.
  13. Command syntax should be simple and intuitive, such that an experienced user (has spent > 1 hour using the application) can memorize the syntax for all basic commands.
  14. Upon rejecting a command, the issue and its fixes should be identified, such that the user can achieve a valid input within n successive tries, where n is the number of errors in the initial input.
  15. If recruitment data cannot be read or fails validation during startup, preserve its original contents in a non-overwriting sibling backup before creating an empty replacement. If safe recovery fails, do not expose commands; identify the preserved data location and recovery steps.
  16. All persistent RecruiterBuddy data should be stored locally in human-readable text files that can be inspected and modified using a plain-text editor. This includes recruitment records, saved candidate status history, and user-defined configuration such as command shortcuts.
  17. If writing updated data fails while the previously saved file remains accessible, RecruiterBuddy should leave that file's contents unchanged.

Glossary

  • Candidate: A person recorded in RecruiterBuddy who has applied for a role opening, regardless of the current stage or outcome of their job application.
  • Candidate status: The recorded stage or outcome of a candidate's recruitment process, as distinct from the status of a role opening.
  • Candidate status history: A chronological record of changes to a candidate's status.
  • Command shortcut: A user-defined abbreviation that represents a command or sequence of commands, rather than a keyboard key combination.
  • Recruitment record: Stored information about a candidate or role opening, including any associated interview details and candidate notes.
  • Role opening: A job vacancy in the recruiter's department tracked in RecruiterBuddy. Here, "role" refers to a job position.
  • Role status: The recorded state of recruitment for a role opening, as distinct from an individual candidate's progress.
