Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Model component

API : Model.java

The partial diagram focuses on role associations. Filtered-view associations and unrelated candidate fields are omitted for clarity.

The Model component,

  • stores candidates (Person) in UniquePersonList and roles (Role) in UniqueRoleList, both owned by AddressBook. ReadOnlyAddressBook exposes unmodifiable observable views of both collections.
  • maintains filtered candidate and role lists in ModelManager, exposed through getFilteredPersonList() and getFilteredRoleList(). The UI observes these lists so additions, replacements, and removals update the relevant list panel.
  • represents each role as an immutable title, required experience level, and RoleStatus (OPEN or CLOSED). One role is one vacancy; no opening count is stored.
  • stores each candidate's association as a RoleTitle, not a separate copy of a Role. Role lookups match titles without case sensitivity.
  • derives role-card summaries through RoleCandidateCounts, an immutable snapshot of candidate-status totals. This helper is omitted from the partial association diagram and is not part of stored role data.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • saves candidates and roles together in the address book JSON file, and user preferences in a separate JSON file. It reads them back into corresponding model objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • uses JsonSerializableAddressBook with JsonAdaptedPerson, JsonAdaptedTag, and JsonAdaptedRole to convert between JSON-compatible values and model objects. A role's saved fields are title, experienceLevel, and status; the status is the exact enum name.
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Role creation and persistence

Role identity and validation

RoleTitle strips surrounding whitespace, validates 1–100 Unicode code points and the allowed characters, and requires at least one letter. ExperienceLevel similarly strips its value and validates 1–50 printable code points, excluding control, format, surrogate, unassigned, line-separator, and paragraph-separator characters. Their constraint messages use the same length constants as their validation, avoiding independently hard-coded limits.

Role#isSameRole compares only titles through RoleTitle#isSameTitle, ignoring case. UniqueRoleList uses that identity to reject duplicates, irrespective of experience level or open/closed status. Full Role#equals also compares experience level and status; it is not the duplicate rule. Internal spaces are not collapsed. The immutable Role constructor without a status creates an OPEN role.

Adding an opening

AddressBookParser routes role to RoleCommandParser, which delegates add to AddRoleCommandParser. The parser tokenises r/ and x/, checks missing fields, reuses ArgumentMultimap#verifyNoDuplicatePrefixesFor, rejects a non-empty preamble, and validates both values through ParserUtil. Missing-prefix errors therefore take precedence over repeated-prefix or invalid-value errors when several problems occur together.

AddRoleCommand checks Model#hasRole before calling Model#addRole. The model updates the underlying observable collection and resets the role filter to show all roles. The command returns Added open role: TITLE. with the default candidate-list view; list role displays the updated roles. Parsing or duplicate rejection leaves the stored records unchanged.

Correcting a role's title or required experience

RoleCommandParser delegates edit to EditRoleCommandParser. The parser reads the displayed-role index with ParserUtil#parseRoleIndex, rejects repeated r/ or x/ prefixes using the existing duplicate-prefix helper, and requires at least one editable field. Supplied values use ParserUtil#parseRoleTitle and ParserUtil#parseExperienceLevel; omitted fields are left unchanged. An invalid index is reported first, followed by duplicate prefixes, missing fields, title validation and experience validation.

EditRoleCommand requires the role view and resolves the index against Model#getFilteredRoleList. It constructs the complete replacement role, preserving its status and omitted fields, then checks the full role collection for a different role with the requested title. Duplicate comparison ignores case and surrounding whitespace, including closed roles; capitalization corrections to the selected role are allowed. The shared duplicate-role message is held in Messages. Corrections never reopen recruitment or merge two openings.

Model#setRole delegates to AddressBook#setRole. The model validates the role replacement through UniqueRoleList before changing either collection. If the title's exact spelling changes, every candidate whose old title matches case-insensitively is updated to the new title using Person#withRole. This includes candidates hidden by the current filter. Their other details and order are unchanged; unrelated candidates retain their existing instances. An experience-only edit does not replace candidate objects. The existing observable lists are retained, so role and candidate cards refresh without new UI components. Filter predicates are retained and reevaluated after list changes.

The result shows Edited role: TITLE. with the updated title and keeps the role view. EditRoleCommand logs accepted corrections and rejected duplicate titles; LogicManager saves both collections through the existing path. Parser or command-validation failures leave records, filters and the saved file unchanged. The existing save-error behavior described below remains unchanged: this is not a transactional filesystem save. Once renamed, a role's old title is available again; no title alias or storage-schema migration is introduced.

Saving and restoring associations

After a command executes successfully, LogicManager#execute asks Storage to save the complete address book, including both collections. This also happens for successful read-only commands. Parsing and command-validation failures do not reach the save call. Save errors become CommandExceptions; earlier in-memory changes are not rolled back. Normal command saves are not transactional and do not create backups. Startup recovery below handles unreadable data separately.

JsonSerializableAddressBook#toModelType reconstructs roles before candidates. Each JsonAdaptedRole validates its required fields and exact OPEN/CLOSED enum name. Duplicate titles are rejected using the same identity rule as the model. Each candidate must then reference an existing role; the loader replaces the candidate's role title with that role's canonical stored title. Closed roles are valid references because closure retains candidates.

An absent roles array is treated as empty, but loading still fails if a candidate lacks a role or references a missing one. A missing candidate status defaults to RESUME, whereas a missing role status is invalid. There is no automatic migration from old contact-only records. Loading validates fields, duplicate records, and references; it does not enforce all command-level recruitment rules, such as the maximum number of hired candidates in hand-edited data.

Protecting unreadable recruitment data

Invalid data is reported as DataLoadingException. JSON null roots and null candidate, role or tag entries also fail loading rather than bypassing the failure path with a null-pointer exception. JsonUtil#fromJsonString reads through a managed Jackson parser and checks for end of input after deserializing the first value. Additional root values or malformed trailing text fail loading; ordinary surrounding whitespace remains valid. This prevents a later save from silently discarding content that Jackson would otherwise ignore. Recovery preserves the entire original file, not just the first object, and does not attempt to combine multiple objects. JsonUtil#readJsonFile returns an empty optional only when the file is known not to exist; an indeterminate existence check does not silently treat an inaccessible file as missing.

MainApp#init attempts recovery after a recruitment-data loading failure. RecruitmentDataRecovery first checks that the source is a regular file without following symbolic links, then moves it to a sibling .bak path. Files.move does not use REPLACE_EXISTING: an existing backup, including one created after the naming decision, is not replaced. A local timestamp in yyyyMMdd-HHmmss-SSS format and then a numbered suffix resolve collisions. The format avoids characters forbidden in Windows filenames. The original bytes are moved, not parsed, repaired or partially imported.

Only after backup succeeds does recovery write an empty JsonSerializableAddressBook at the original path using CREATE_NEW. This refuses to overwrite a file that appears during recovery. Persisting the empty replacement before initializing commands also makes the next startup stay empty, even if the user exits without executing a command. The existing missing-file sample-data policy is not used for this recovery path.

MainApp#start asks UiManager to show a warning on the JavaFX thread before opening the command window. The warning names the full backup and replacement paths and explains manual restoration. No automatic merge is attempted: users must preserve new records separately before restoring. StartupDataNotice holds the notification text and fatal/non-fatal outcome independently of JavaFX. Lifecycle tests capture those real notices through the notification boundary; separate notice tests check paths and restoration instructions without substituting the message-generation logic.

If backup or replacement creation throws an I/O or security exception, initialization returns before creating the model, logic or command UI. The startup error names the original path, failure reason, and backup path if the move succeeded. JavaFX shuts down after dismissal. A directory or symbolic link is not moved. MainApp#stop skips preference saving when no model was initialized. Preference loading still runs before recruitment data is loaded. Preference files use the same single-root JSON check; invalid preferences retain the existing default-settings fallback rather than using recruitment-data backup recovery.

Recovery preserves the source before exposing any command that can reach the normal save path. If recovery cannot complete safely, startup remains blocked rather than risking the original or its backup. If the file is genuinely absent instead, startup still uses `SampleDataUtil#getSampleAddressBook`. A valid empty file loads empty lists, not sample data. Recovery diagnostics follow the same lifecycle: `MainApp` emits a loading `WARNING`, `RecruitmentDataRecovery` records each completed backup and replacement at `INFO`, and unsafe recovery ends with a `SEVERE` event from `MainApp`. Success messages name the paths actually used and are not emitted for a stage that failed. Existing startup and recovery tests now check these events alongside preserved file contents and the absence of a command UI after failure. The shared `LogCapture` test utility restores logging configuration after each capture. See [Recovery diagnostics](Logging.md#recruitment-data-recovery-diagnostics) for interpretation and privacy limitations; no extra production logging or recovery-policy change is needed. ### Role lifecycle and candidate safeguards #### Closing recruitment `RoleCommandParser` delegates `close` to `CloseRoleCommandParser`. Close and delete share `ParserUtil#parseRoleIndex` to reject missing, invalid, or extra index arguments consistently. `CloseRoleCommand` first checks `Model#isRoleListDisplayed`, then resolves the index against `Model#getFilteredRoleList` and rejects an already closed role. Candidate checks use the complete `ReadOnlyAddressBook#getPersonList`, not the filtered candidate list, matching role titles without case sensitivity. `Status#isPending` classifies statuses `RESUME`, `INTERVIEW`, `OFFER` and `DECISION` as pending. Closure rejects pending candidates with their count, then rejects more than one hired candidate. No candidates, or no hired candidate, is allowed. After validation, `Model#setRole` replaces the immutable role with a `CLOSED` copy. Candidate records and statuses remain unchanged. The observable role list refreshes, the command result keeps it displayed, and `LogicManager` saves the change. `AddCommand` rejects new candidates for closed roles. #### Deleting an unused role `RoleCommandParser` delegates `delete` to `DeleteRoleCommandParser`. `DeleteRoleCommand` applies the same displayed-list and index guards, then counts associated candidates across all stored records. Any associated candidate blocks deletion, irrespective of status or visibility; the error includes their count. An empty role may be deleted whether `OPEN` or `CLOSED`. Deletion goes through `Model#deleteRole`, `AddressBook#removeRole`, and `UniqueRoleList#remove`. The observable list refreshes and its indices update; the result keeps the role list displayed. `LogicManager` saves the removal. Deletion releases the title for reuse but never deletes, detaches, or reassigns candidates. It is immediate and has no undo operation in the MVP. #### Status changes and one hire per role Before assigning `HIRED`, `StatusCommand` uses `CandidateRoleChecks` to check all stored candidates for another hire with a case-insensitively matching role title, excluding the selected candidate by candidate identity. Reapplying `HIRED` to that candidate is allowed if there is no other hire. Moving an existing hire to another permitted status frees the vacancy; hiring a candidate never closes the role automatically. Before assigning a pending status, the command looks up the candidate's role and rejects the change if the role is closed. Final-to-pending corrections remain available for open roles. Corrections between final outcomes remain available for closed roles, subject to the hiring guard. Both guards run before replacing a candidate or changing filters. Rejected commands do not trigger saving. #### Keeping displayed indices aligned with the UI After successful execution and saving, `LogicManager` sets `Model#isRoleListDisplayed` from `CommandResult#isShowRoleList`, the same value `MainWindow` uses to select the visible list. A save failure does not roll back an earlier in-memory mutation, as explained in [Saving and restoring associations](#saving-and-restoring-associations). Listing roles retains the candidate filter. Candidate-index commands use the view flag rather than an artificial empty candidate list. If a successful candidate addition switches the UI to candidates, role edit, close, and delete reject indices until `list role` is run again. See the [role management manual checks](#role-management) for reproducible regression scenarios. ### Candidate-status totals on role cards `RoleCandidateCounts` scans a supplied candidate collection for a case-insensitively matching `RoleTitle`, then snapshots counts by `Status`. Pending totals use `Status#isPending` rather than hard-coded pending-status names. Each candidate contributes once, and an absent category returns zero. The summary reports actual records, including any inconsistent hand-edited hire counts; it never changes statuses or enforces command-level recruitment rules. `Logic#getPersonList` exposes the address book's unmodifiable observable candidate list, not the filtered list used by the candidate panel. `MainWindow` passes it to `RoleListPanel` alongside the existing observable role list. A panel-lifetime candidate listener refreshes the role list after additions, replacements, removals, and resets. List cells construct fresh summaries when rendering their roles, including when scrolling or returning from the candidate view. Listeners are not attached to individual recycled cells. Role replacements still use the existing role-list binding. `RoleCard` displays four explicit labels in a wrapping `FlowPane`. Cards bind their width to the available list-cell width, so long role details wrap without forcing horizontal scrolling. Role indices retain their full width beside wrapped titles. Both open and closed roles use the same calculation. Counts are not cached in `Role` or saved to JSON, so loading data reconstructs them without a schema migration or a second source of truth. Candidate filters, role order, indices, and command feedback are unchanged. Unit tests cover classification, title matching, empty states, snapshots, and mixed-role data. Logic integration tests check unfiltered observation, status changes, additions, deletion, role reassignment through the edit command and model API, resets, and reload. It uses `ParserUtil#parseRoleTitle` for the existing title constraints and stores the result in `EditPersonDescriptor`, including its copy, equality and diagnostic-string behaviour. `EditCommand` resolves an explicitly requested role through `Model#findRole` before replacing any records or changing filters. A missing role is rejected; a different role must be open. The source may be open or closed, and selecting the existing role remains a permitted no-op. Resolution uses case-insensitive matching and the stored role's canonical spelling. Omitting `r/` preserves the role. The shared `EditCommand#isRoleChanged` predicate keeps the closed-destination and hiring guards consistent about whether the operation actually transfers the candidate. The edited immutable `Person` keeps its status and note, and keeps every other field not explicitly edited. The existing candidate-identity duplicate check is unchanged. For a real role transfer, `CandidateRoleChecks#verifyHiringAllowed` rejects a `HIRED` candidate if another stored candidate for the destination is hired. It uses all records, not the filtered list, and excludes the original candidate by identity rather than the edited name. `StatusCommand` shares this check to prevent the two workflows from implementing different single-vacancy rules. After validation succeeds, `Model#setPerson` updates the observable candidate collection and the candidate filter resets to show all records. The existing `Edited candidate: ...` result formats the updated candidate, including the new name and canonical role. Normal `LogicManager` saving persists the association without a JSON schema change. Validation failures leave records and filters unchanged and do not save. Neither role's status changes automatically. ### Role workflow diagnostics and internal checks Role commands and candidate-role transfers reuse `LogsCenter`, with `INFO` for successful in-memory changes and `FINE` for expected recruitment-rule rejections. Command formats, success/error messages, UI behavior and the storage schema are unchanged. ### \[Proposed\] Undo/redo feature #### Proposed Implementation The proposed undo/redo mechanism is facilitated by `VersionedAddressBook`. It extends `AddressBook` with an undo/redo history, stored internally as an `addressBookStateList` and `currentStatePointer`. Additionally, it implements the following operations: * `VersionedAddressBook#commit()` -- Saves the current address book state in its history. * `VersionedAddressBook#undo()` -- Restores the previous address book state from its history. * `VersionedAddressBook#redo()` -- Restores a previously undone address book state from its history. These operations are exposed in the `Model` interface as `Model#commitAddressBook()`, `Model#undoAddressBook()` and `Model#redoAddressBook()` respectively. Given below is an example usage scenario and how the undo/redo mechanism behaves at each step. Step 1. The user launches the application for the first time. The `VersionedAddressBook` will be initialized with the initial address book state, and the `currentStatePointer` pointing to that single address book state. Step 2. The user executes `delete 5` command to delete the 5th person in the address book. The `delete` command calls `Model#commitAddressBook()`, causing the modified state of the address book after the `delete 5` command executes to be saved in the `addressBookStateList`, and the `currentStatePointer` is shifted to the newly inserted address book state. Step 3. The user executes `add n/David …​` to add a new person. The `add` command also calls `Model#commitAddressBook()`, causing another modified address book state to be saved into the `addressBookStateList`.
**Note:** If a command fails its execution, it will not call `Model#commitAddressBook()`, so the address book state will not be saved into the `addressBookStateList`.
Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the `undo` command. The `undo` command will call `Model#undoAddressBook()`, which will shift the `currentStatePointer` once to the left, pointing it to the previous address book state, and restores the address book to that state.
**Note:** If the `currentStatePointer` is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The `undo` command uses `Model#canUndoAddressBook()` to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Interview dates and times have their own field, described in [Candidate interviews](#candidate-interviews). An empty note means the candidate has no note, and the candidate card hides it. #### Recording a note `NoteCommandParser` splits the arguments into the first word, which is parsed as the index, and the rest, which is trimmed and becomes the note. It does not use `ArgumentTokenizer`, so the note can contain text that looks like a prefix, such as `t/` or `n/`. An empty remainder gives an empty `Note`, so `note 1` clears the first candidate's note. `NoteCommand#execute` looks up the candidate in the displayed candidate list and replaces it with a copy that has the new note. Other commands that rebuild a `Person`, such as `edit`, `status`, and `interview`, copy the existing note across, so they never change it. Notes are stored as the `note` field of each candidate in the JSON data file. A candidate saved without a `note` field loads with an empty note. #### Design considerations **Aspect: How the note is entered** * **Alternative 1 (current choice):** A separate `note INDEX [NOTE]` command that takes everything after the index. * Pros: Any text can be stored, including text that looks like a prefix. * Cons: A note cannot be given when the candidate is first added, so it takes a second command. * **Alternative 2:** An `nt/NOTE` prefix on `add` and `edit`. * Pros: Consistent with the other candidate fields. * Cons: The tokenizer ends the note at the next prefix. For example, `nt/Discuss t/java` would save the note `Discuss` and add a `java` tag, so valid notes are silently changed. This alternative was implemented and then removed for this reason. ### Candidate interviews Each `Person` has an `Interview`, which holds the date and time of the candidate's interview, to the minute. A candidate with no interview has `Interview.NONE`, so no code needs to handle a `null` interview. The candidate card shows the interview as `Interview: YYYY-MM-DD HH:MM`, and hides the line for `Interview.NONE`. #### Validating a date and time `Interview` accepts only zero-padded `YYYY-MM-DD HH:MM` values that are real dates and valid 24-hour times. It checks a value in two steps, so that each kind of mistake gets its own error message: 1. `Interview#isValidFormat` checks the shape with a regular expression. A value such as `2026-10-20 9:00` fails here, and the user is told the expected format. 2. `Interview#isValidDateTime` parses the value with the pattern `uuuu-MM-dd HH:mm` and `ResolverStyle.STRICT`. A value with the right shape but an impossible date or time, such as `2026-02-30` or `24:00`, fails here, and the user is told the value does not exist. Strict resolving is needed because the default resolver silently adjusts `2026-02-30` to `2026-02-28`. The pattern uses `uuuu` (year) instead of `yyyy` (year of era), because strict resolving rejects every `yyyy` year that has no era. The `Interview` constructor enforces both checks with `checkArgument`, so an invalid interview cannot be created even when assertions are disabled. Past dates are allowed, so recruiters can record interviews that have already happened. #### Scheduling or clearing an interview `InterviewCommandParser` tokenizes the arguments with the `d/` prefix. The preamble must be exactly one index. If `d/` is present, `ParserUtil#parseInterview` runs the two checks above and creates the `Interview`. If `d/` is left out, the parser uses `Interview.NONE`, so `interview 1` clears the first candidate's interview. An empty `d/` is rejected with the format error instead of clearing the interview, so a user who forgets to type the date does not lose the existing one. `InterviewCommand#execute` looks up the candidate in the displayed candidate list and replaces it with `Person#withInterview`, a copy that has the new interview. Unlike `note`, it does not reset the candidate filter, so a recruiter can schedule interviews for a filtered list by its displayed numbers. Clearing a candidate with no interview, or giving the same date and time again, succeeds without changing the data, as `note` does for notes. Other commands that rebuild a `Person`, such as `edit`, `note`, and `status`, copy the existing interview across, so they never change it. #### Saving and loading interviews Interviews are stored as the `interview` field of each candidate in the JSON data file, in the same `YYYY-MM-DD HH:MM` form. `Interview.NONE` is saved as an empty string. When loading, a missing, `null`, or empty `interview` field gives `Interview.NONE`, so data files saved before interviews existed still load. Any other value goes through the same two checks, and an invalid value stops the file from loading, as an invalid phone number does. #### Design considerations **Aspect: Where the interview is stored** * **Alternative 1 (current choice):** A separate `Interview` field with its own command. * Pros: The date and time are checked, so impossible or mistyped slots are rejected. The value can later be used to sort candidates by interview time. * Cons: Every place that rebuilds a `Person` must copy the new field, or that command would silently clear the interview. * **Alternative 2:** Keep interviews in the free-text note. * Pros: No new field or command. * Cons: Nothing checks the date, and the date cannot be compared or sorted. **Aspect: How "no interview" is represented** * **Alternative 1 (current choice):** An `Interview.NONE` value, whose date and time is held in a private nullable field and returned as an `Optional`. * Pros: `Person` fields are never `null`, and the `null` never leaves the `Interview` class. * Cons: Code that needs the date and time must handle the empty `Optional`. * **Alternative 2:** A sentinel date, such as `0000-01-01 00:00`. * Pros: Every interview has a real `LocalDateTime`. * Cons: The sentinel could be shown or sorted as if it were a real interview, and a user could enter the same value. ### \[Proposed\] Data archiving _{Explain here how the data archiving feature will be implemented}_ -------------------------------------------------------------------------------------------------------------------- ##
